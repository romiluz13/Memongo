# Correctness & Concurrency — Deep Review Findings

Scope: async bugs, error handling, type-safety holes, resource lifecycle, concurrency primitives, transaction use, test realism. Files reviewed in full or targeted chunks: mongodb-manager.ts (~3,500 of 11,265 LOC read, all concurrency-relevant regions), mongodb-sync.ts, mongodb-consolidator.ts, mongodb-query-cache.ts, mongodb-events.ts, mongodb-episodes.ts, mongodb-memory-jobs.ts, mongodb-transactions.ts, mongodb-graph.ts (extractAndUpsertEntities), mongodb-structured-memory.ts (writeStructuredMemory), mongodb-embedding-retry.ts, mongodb-access-tracker.ts, mongodb-change-stream.ts, search-manager.ts, embeddings.ts, embeddings-gemini.ts, internal.ts, mongodb-telemetry.ts, mongodb-entity-extractor.ts (timeout), mongodb-llm-enrichment.ts (worker pool), apps/api/src/app.ts, apps/api/src/routes/v1.ts, apps/mcp/src/server.ts, packages/memory-bridge/src/memongo-bridge.ts, packages/client/src/client.ts, mongodb-manager.test.ts, mongodb-consolidator.test.ts, apps/api/src/app.test.ts, CI workflows.

## Findings

- [SEV: high] Consolidation gate is a TOCTOU read-then-insert — no distributed lock, double-processing across replicas
  - Where: `packages/memory-engine/src/mongodb-consolidator.ts:313` (findOne last run with `status: { $in: ["completed","running"] }`) then `:330` (insertOne `status: "running"`); entry point `packages/memory-engine/src/mongodb-manager.ts:8144-8179`; exposed over HTTP and MCP via `packages/memory-bridge/src/memongo-bridge.ts:1163` (`memongoBridgeConsolidate`).
  - What: The Phase-0 rate-limit gate reads the most recent run, then inserts a new "running" row. Two concurrent callers (two API replicas, or `/v1/consolidate` racing the MCP `memongo_consolidate` tool) both read "no recent run", both insert, both run the full pipeline. There is no unique partial index on `(agentId, scope, scopeRef, status:"running")` and no lease/claim on the run row.
  - Why it matters: A doubled run (a) re-promotes facts racing the `$vectorSearch` NOOP check at `mongodb-consolidator.ts:572-609` — the Atlas vector index is near-real-time, so run B cannot see run A's just-written facts and both decide ADD, producing duplicate structured facts; (b) double-runs Phase-2.5 entity extraction over the same events (`:791-817`, a `Promise.allSettled` fan-out of up to 100 concurrent extractions — a thundering herd on the connection pool all by itself); (c) races the prune phase invalidations at `:960-1000`; (d) burns 2× LLM tokens in the deduction/induction phases. Separately, a crashed run leaves its row `status:"running"` forever — no stale-run recovery — and after `minIntervalMs` (1 h) it silently stops blocking anything, so the "lock" decays to nothing.
  - Recommendation: Claim the run atomically — `findOneAndUpdate` with a lease (`leaseExpiresAt`) on a single per-(agentId,scope,scopeRef) gate document, or a unique partial index on active runs; fence completion on the lease token like `mongodb-memory-jobs.ts` already does for extraction jobs. Reap stale "running" rows.

- [SEV: high] Client retries non-idempotent writes; the write path can throw AFTER the event is persisted → duplicate events
  - Where: `packages/client/src/client.ts:124-131` (`shouldRetryStatus` = 429|503, retries any request including POST `/v1/add` and `/v1/write-event`); `packages/memory-engine/src/mongodb-manager.ts:8984` (`throw new Error("failed to release staged extraction job: ...")` after `writeEvent`, `projectEventChunk`, and entity extraction have all committed); route `apps/api/src/routes/v1.ts:1492-1526, 1530-1603`.
  - What: `writeConversationEvent` generates a fresh `eventId` per attempt (`randomUUID` inside `execute`, `mongodb-manager.ts:8839`), persists the event, then can still throw (staged-job release failure). The API maps that to 500 `ADD_FAILED`/`WRITE_EVENT_FAILED`. The client then retries the POST — writing a second, identical-body event with a new eventId. Any 503 that arrives after server-side commit (proxy timeout, derivation failure) duplicates the memory. The API accepts no client-supplied idempotency key.
  - Why it matters: Duplicate memories surface in search, double-count events in consolidation/episodes, and erode trust in `sourceEventIds`-based provenance. This is the classic retry-without-idempotency hole, and it is directly reachable via a code path that already exists in the manager.
  - Recommendation: Accept a client-supplied `eventId`/`idempotencyKey` on `/v1/add` and `/v1/write-event` (`writeEvent` is already `$setOnInsert`-upsert idempotent on `eventId` — `mongodb-events.ts:191-200`), and only auto-retry idempotent requests (or retry with the same key). Never throw after commit for post-write bookkeeping failures — log and let the outbox repair pass (`repairExtractionOutbox`) recover.

- [SEV: high] One MongoClient per agent, cached forever; shutdown race leaks an initialized manager
  - Where: `packages/memory-engine/src/search-manager.ts:15` (`MONGODB_MANAGER_CACHE`), `:94-104` (in-flight dedupe then unconditional `MONGODB_MANAGER_CACHE.set`), `:114-127` (`closeAllMemorySearchManagers` clears `INFLIGHT_INIT` and the cache without awaiting in-flight creates); each manager owns and closes its own client (`packages/memory-engine/src/mongodb-manager.ts:9222-9228`).
  - What: Every distinct agentId+config gets a full `MongoDBMemoryManager` with its own `MongoClient` (default pool 100), chokidar watcher, change stream, and setInterval timers. The cache has no eviction. Separately, if `closeAllMemorySearchManagers()` runs while `initializeManager` is in flight, the late-resolving init does `MONGODB_MANAGER_CACHE.set(cacheKey, manager)` on an already-cleared map — that manager is never closed: client, watcher, and intervals leak past shutdown.
  - Why it matters: On a multi-tenant API server, N agents = N connection pools pointed at the same cluster (MongoDB's own guidance is ONE client per process; each connection ≈ 1 MB server RAM, formula: instances × (maxPoolSize+2) × members). The shutdown race defeats the graceful-shutdown work in `apps/api/src/app.ts:340-431`.
  - Recommendation: Share one `MongoClient` across managers (pass it in, key managers by agent but pool connections once), bound/evict the manager map, and make close await or cancel `INFLIGHT_INIT` before clearing.

- [SEV: high] Sync's non-transactional path permanently loses chunks: partial bulkWrite failure is masked by the metadata hash
  - Where: `packages/memory-engine/src/mongodb-sync.ts:204-213` (`upsertChunks` logs `writeErrors` and returns `applied`), `:299-310` (non-transactional branch of `syncFileAtomically` then calls `upsertFileMetadata` with the NEW hash), same pattern for sessions at `:350`.
  - What: On standalone mongod (transactions unsupported) or when `client` is not passed, a partially-failed chunk bulkWrite (e.g., one oversized document, one duplicate-key) is only logged. File metadata is then written with the new content hash, so the next sync sees `stored.hash === file.hash` and skips the file. The missing chunks are never re-attempted until the file changes again. The transactional path is all-or-nothing and safe; this path is the opposite.
  - Why it matters: Silent, permanent search-coverage gaps — memory files exist on disk and in `files`, but their chunks are absent from recall. Exactly the "partial failure leaves corrupt state" class, and invisible in stats (filesProcessed counts it as success).
  - Recommendation: If `writeErrors.length > 0`, do not write metadata (or write the OLD hash) so the file is retried; better, retry failed ops individually and only mark the file synced when every chunk op applied.

- [SEV: high] Episode materialization TOCTOU: the summarized event set and the marked-consolidated set diverge
  - Where: `packages/memory-engine/src/mongodb-episodes.ts:754` (`resolveTriggeredEpisodeWindow` picks `episodeEvents`), `:205` (`materializeEpisode` re-queries with `getEventsByTimeRange` over `[start,end]`, limit 1000), `:786` (`markEventsConsolidated` only over the original `episodeEvents`); rate-limit check at `:715-721` is also read-then-write.
  - What: `checkAutoEpisodeTriggers` selects a window of unconsolidated events, then `materializeEpisode` re-reads events by time range — picking up any events written between selection and materialization — and summarizes THOSE (`sourceEventIds` = re-queried set). `markEventsConsolidated` then marks only the originally-selected subset. Late-arriving events end up inside an episode's content/hash but remain `consolidatedAt: {$exists:false}`, so the next trigger summarizes them again into a second episode (different event set → different `sourceEventsHash` → no dedupe).
  - Why it matters: Duplicate/overlapping episodes over the same conversations — the exact failure the content-hash identity (`:280-330`) was built to prevent, defeated by the check/mark skew. Concurrent triggers additionally both pass the rate-limit read at `:721`.
  - Recommendation: Materialize from the selected `episodeEvents` (pass them in; don't re-query), or mark exactly the set recorded in `sourceEventIds`; claim the trigger with the same lease pattern as memory jobs.

- [SEV: medium] Extraction job lease fencing is advisory — writes happen before the lease check, and re-runs inflate counts
  - Where: `packages/memory-engine/src/mongodb-manager.ts:8507` (`if (leaseLost)` checked only AFTER `extractAndUpsertEntities` and `promoteDerivedMemoryFromEvent` have committed); completion fencing `packages/memory-engine/src/mongodb-memory-jobs.ts:217-238` (`leaseExpiresAt: { $gt: now }` + `leaseToken`).
  - What: The lease (60 s, heartbeat 20 s — `mongodb-manager.ts:329-331`) can be lost while long LLM promotion runs. The worker detects the loss only after the entity upserts and derived-memory writes are done; a second worker that re-claimed the expired lease repeats the same work. `mentionCount` is protected by the `$cond`-on-`sourceEventIds` pipeline update (`mongodb-graph.ts:1504-1540`), but `writeStructuredMemory`'s same-value re-mention path `$inc`s `reinforcementCount` on every run (`mongodb-structured-memory.ts:795-807`), so duplicate execution inflates reinforcement and doubles LLM spend. `completeClaimedMemoryJob` then no-ops (returns false) and only a `log.warn` records it.
  - Why it matters: Fencing tokens only guard the status row, not the side effects — the job system guarantees at-least-once execution but the downstream writes are only partially idempotent.
  - Recommendation: Pass `eventReceiptIds` into derived-memory writes so `hasProcessedSourceEvents` short-circuits re-execution (`mongodb-structured-memory.ts:765-773` already supports it), and check `leaseLost` before each side-effecting stage, not once at the end.

- [SEV: medium] Entity bulkWrite upsert race: E11000 swallowed as "partial failure", entity update silently dropped
  - Where: `packages/memory-engine/src/mongodb-graph.ts:1562-1568` (`catch (bulkErr) { log.warn("bulkWrite entity upserts partial failure") }` then execution continues to relations and returns success).
  - What: Two concurrent extractions (write path + background job, or two dreamer runs) upserting the same `entityId` can both take the insert path; the unique index rejects one with E11000 inside the unordered bulkWrite. The error is caught and logged; the losing op's mention/sourceEventIds update is never retried.
  - Why it matters: Under exactly the concurrent conditions the job system creates, entity stats silently under-count and the projection run still records "ok". The codebase already solved this exact pattern elsewhere (`persistWithDuplicateKeyRetry`, `mongodb-structured-memory.ts:929-945`; episode upsert retry, `mongodb-episodes.ts:311-323`).
  - Recommendation: Retry duplicate-key writeErrors as plain updates, matching the P1-2 pattern used for structured memory and episodes.

- [SEV: medium] writeStructuredMemory revision TOCTOU in the non-transactional path
  - Where: `packages/memory-engine/src/mongodb-structured-memory.ts:746-758` (findOne identity), `:876-926` (`revision: currentRevision + 1` via `$set`); only the insert race is retried (`:934-945`). The consolidator calls it WITHOUT `client` (`mongodb-consolidator.ts:654-666` and the reasoning-phase write), forcing the non-transactional path.
  - What: Read-modify-write on `revision`/`validFrom`/`reinforcementCount` history: two concurrent same-key writes both read revision N, both write N+1 with different values; last writer wins, one revision history doc (inserted at `:833`) describes a value that was never current. With `client` present a transaction + `withTransaction` retry masks this; without it, nothing does.
  - Why it matters: Revision numbers and `supersedes` chains are provenance data; corrupt chains break "as of T" queries and conflict resolution.
  - Recommendation: Make the revision bump atomic — e.g., pipeline update computing `revision: {$add: ["$revision", 1]}` server-side, or always route through a shared client/transaction.

- [SEV: medium] Type-safety holes at system boundaries
  - Where: `apps/api/src/routes/v1.ts:1643` (`entry as StructuredMemoryEntry` straight from client JSON; no runtime validation of `type`/`key`/`value` — a missing key lands in the DB identity filter as `undefined`), same for `/write-procedure` at `:1665`; `packages/memory-bridge/src/memongo-bridge.ts:1262-1268` (`results[0].value : ({} as any)` — fabricated empty profile/bundle returned as real data, only `partial: true` flags it); `apps/mcp/src/server.ts:1709` (`args.scope as "user"` — any string cast to MemoryScope); pervasive `as unknown as CanonicalEvent[]`-style casts on DB reads (`mongodb-events.ts:263, 304, 343, 402, 449`).
  - What: No zod/schema validation at the HTTP/MCP write boundary for structured entries; bridge fabricates typed objects from failed sub-calls; DB documents are force-cast without runtime checks.
  - Why it matters: A malformed `entry` writes garbage identity keys into `structured_mem` that the identity filter can never match again (orphan duplicates on retry); `as any` defeats the strict-typing guideline at exactly the layer that returns data to callers.
  - Recommendation: Validate `entry` at the route (required `type`, non-empty `key`/`value`, enum scope) before casting; type the `/state` fallback as partial variants instead of `{} as any`.

- [SEV: medium] Client SDK has no request timeout; Retry-After ignored
  - Where: `packages/client/src/client.ts:118-133` (`fetch` with no `AbortSignal.timeout`; fixed `sleep(200 * attempt)` backoff ignoring the API's `Retry-After` header set at `apps/api/src/app.ts:113`).
  - What: A hung API connection hangs every MCP tool call indefinitely (the MCP server awaits the client, `apps/mcp/src/server.ts:2068`); 429 responses are retried on a fixed schedule regardless of the server's requested wait.
  - Why it matters: "It actually works" — an agent using the MCP server freezes its tool loop with no diagnostic when the API wedges; fixed-backoff retries amplify rate-limit pressure.
  - Recommendation: `AbortSignal.timeout(opts.timeoutMs ?? 30_000)` per request, honor `Retry-After` on 429/503.

- [SEV: medium] Query cache: stampede on miss, per-miss metadata round trip, measurement bug
  - Where: `packages/memory-engine/src/mongodb-query-cache.ts:206` (`estimatedDocumentCount()` on every tier-2 check), `:258-273` (semantic probe is a server-side embedding round trip capped at 1.5 s), `:178` (`exactMs = Date.now() - cacheStart` instead of `- exactStart` in the tier-1 catch), `:313-381` (`writeCache` fire-and-forget).
  - What: Every cache miss pays an extra count round trip, then potentially an embedding probe, before the real search runs. There is no single-flight: N concurrent identical queries all miss, all run full hybrid search, all upsert the same cache key. The hit-count increments and cache writes are fire-and-forget (errors only logged).
  - Why it matters: On cold cache or TTL expiry waves, the cache AMPLIFIES load (probe + full search + embedding) instead of absorbing it — thundering herd on the exact hot path it exists to protect.
  - Recommendation: Single-flight per queryHash (in-process promise map), skip tier 2 when a cheaper heuristic says miss, and consider gating the semantic probe behind a minimum expected win.

- [SEV: medium] Lifecycle: unref inconsistency keeps processes alive; runContexts map leaks
  - Where: `packages/memory-engine/src/mongodb-manager.ts:7577` (`this.watchTimer = setTimeout(...)` — NOT unref'd, unlike the heartbeat/worker timers at `:8417, :8683`); `packages/memory-engine/src/mongodb-access-tracker.ts:91` (flush `setInterval` not unref'd); `packages/memory-engine/src/mongodb-manager.ts:8755-8757` (`memoryJobRunContexts.set` for every scheduled job with a runContext; entries deleted only when the job actually runs, `:8635` — jobs never claimed (worker stopped before drain) leak their entry for the process lifetime).
  - What: A manager whose `close()` is skipped (crash, the search-manager shutdown race above) pins the event loop via these timers; benchmark runs accumulate stale runContext entries.
  - Why it matters: Process-hang-on-exit class of bug; slow unbounded map growth on long-lived API processes.
  - Recommendation: unref both timers; delete runContext entries when a job becomes non-recoverable or completes/fails terminally.

- [SEV: low] Consolidation run rows never recover from crash
  - Where: `packages/memory-engine/src/mongodb-consolidator.ts:330-336` (insert `status: "running"`, updated to completed/failed only on the happy/failure paths).
  - What: A process crash mid-run leaves `status:"running"` forever; after `minIntervalMs` the gate ignores it, so it neither blocks nor is reported — a silent dead letter.
  - Recommendation: Reap stale running rows on startup or treat `startedAt` older than a threshold as failed.

- [SEV: low] Literal NUL (0x00) bytes embedded in source as string separators break tooling
  - Where: `packages/memory-engine/src/mongodb-consolidator.ts:894` (`` `${scope ?? ""} ${scopeRef ?? ""}` `` — the "space" is a literal NUL), `packages/memory-engine/src/mongodb-episodes.ts:176` (`.join(" ")` — separator is a literal NUL).
  - What: Each file contains exactly one 0x00 byte (verified byte-level). ripgrep/grep classify both files as binary and skip them — this review's own tooling failed on both files until searched with binary flags.
  - Why it matters: Harmony/tooling: two of the most concurrency-critical files are invisible to standard code search; any grep-based audit, CI lint, or IDE search silently misses them.
  - Recommendation: Use `"\0"` escape sequences instead of literal NUL bytes.

- [SEV: low] Error-shape disharmony across the API → MCP boundary
  - Where: `apps/api/src/lib/errors.ts` via `apps/api/src/routes/v1.ts:50` (`{ error: { code, message } }`) vs `apps/mcp/src/server.ts:2068-2071` (`jsonResult({ error: message }, true)` — bare string, no code); `packages/client/src/client.ts:133` wraps the raw body text.
  - What: Three different error shapes at three layers; MCP consumers lose the machine-readable `code` the API carefully produces.
  - Recommendation: Parse the API error body in the client (expose `code` on `MemongoClientError`) and propagate `{ code, message }` through MCP tool errors.

- [SEV: medium] Test realism: the three biggest suites mock away exactly the layers this review finds bugs in
  - Where: `packages/memory-engine/src/mongodb-manager.test.ts` (143 tests / 7,243 LOC; `vi.mock` of `mongodb-schema.js` — ALL collection accessors are `vi.fn()` (lines 260-290), `mongodb-memory-jobs.js` entirely mocked (311-322), plus query-cache, consolidator, derived-memory, events); `packages/memory-engine/src/mongodb-consolidator.test.ts` (44 tests; `vi.mock` of `writeStructuredMemory`, `scanNovelty`, graph extraction, llm-enrichment (lines 52-89); collections are canned `mockCollection`/`mockDb` objects, e.g. lines 107-124); `apps/api/src/app.test.ts` (106 tests; `@memongo/memory-bridge` fully mocked, line 50).
  - What: The manager suite asserts orchestration wiring against mocked collections — the writeQueue serialization, job lease/fencing, outbox release, and cache invalidation paths are never executed against a real or even fake-but-stateful store. The consolidator suite cannot see the Phase-0 gate TOCTOU, the NOOP-vs-ADD race, or the prune invalidation behavior because every DB interaction returns canned values. The API suite never exercises engine→bridge→route error propagation (e.g., the throw-after-persist 500 in finding 2).
  - Why it matters: These suites give false confidence on precisely the concurrency-critical paths. Mitigating factors: `test:e2e:tier-a` runs in CI against a real MongoDB (`.github/workflows/ci.yml:78`) and includes `mongodb-memory-jobs.e2e.test.ts`, and full e2e runs nightly — but the default `bun run test` (and publish.yml:35) runs only the mocked suites.
  - Recommendation: Add a stateful in-memory Mongo fake (or mongodb-memory-server) for the manager write path and consolidator gate; assert behavior (what's in the collections), not call wiring; add one integration test proving a post-persist failure does not produce a client-visible retry-duplicate.

## Harmony note

The concurrency story is two different systems with two different maturity levels living side by side. The extraction-job subsystem (memory-jobs + manager worker) is genuinely well designed: atomic `findOneAndUpdate` claiming, server-time leases, token fencing on renew/complete, a staged-job outbox with repair, serialized write/derivation queues, graceful close ordering. But consolidation, episode triggering, and structured-memory revisioning — the other writers — use ad-hoc read-then-write gates with no lease, no fencing, and no idempotency keys, and they are reachable concurrently through the same API/MCP surface. The seams are also misaligned vertically: the engine can throw after commit, the bridge passes errors through verbatim, the API flattens them to 500, and the client retries them — each layer individually reasonable, jointly a duplicate-write machine. The engine's careful `$setOnInsert`/`sourceEventsHash` idempotency work shows the right instinct; it just isn't wired to the transport boundaries (no caller-supplied keys) or applied to the dreamer/episode paths. One shared client, one lease primitive, and one error envelope would make the organism feel like one design.
