## Notes

- **PI-01**: The standard-scope gate is purely display-category based (`tool-registry.ts:60-68`, `server.ts:407-410`). Alias tools survive the standard filter whenever `MEMONGO_MCP_ALIASES=1`, and `handleToolCall` routes them to the identical SDK operations as the admin-gated canonical names with no per-operation authorization re-check.
- **PI-02**: The cache itself was hardened since the audit (full SHA-256 over the identity tuple, LRU refresh — `cache-identity.ts`), but the finding's core defect is the request identity, not the cache: the wire call still collapses user into agent and offers no scopeRef channel, so a shared explicit agentId still merges users server-side. Defect as described still present.
- **PI-04**: Three independent mismatches all remain: (a) block label sets disjoint client-vs-engine, (b) required `title/content/sourcePaths` never produced, (c) quarantine 202 typed as carrying `MemongoLifecycleItem` fields. Partial-state `{}`+`partial:true` (`memongo-bridge.ts:1049-1062`) also still narrower than the client's promised response.
- **PI-05**: P2.3/C-008 fixed the save-scope-vs-search-scope divergence (both default to `agent`), so default saves are now findable by default search. Remaining: server-side scopeRef filter still unused (the in-code claim "search API doesn't expose a direct scopeRef filter" at `index.ts:311-313` is stale — `searchDetailed` accepts `scopeRef` at `client.ts:767`); basename identity collisions and the worktree-identity comment/code mismatch persist.
- **PI-06**: The collision construct is unchanged. The audit's own proof gap (no live Pi session driven) also remains unclosed — live impact still needs a persisted-session resume test.
- **PI-07**: `retryProbeUntilAvailable` supports `onHealed`, but `index.ts:230` invokes it without the callback, so nothing re-arms prefetch or re-attempts injection after the API heals.
- **PI-10** sub-items, all still present:
