# M2 failure matrix

Every entry point that the M2 call-path inventory marks REBUILD or TYPED, mapped to the tests on branch `integration/m2-20261019` that pin its failure behavior. Source: `call-path-inventory.md` (plan decision 11), 108 rows: 40 REBUILD and 68 TYPED, counted by primary disposition. KEEP rows are not listed.

The rule behind every row is the same: a failure, a denial or an absent capability surfaces as a typed failure. A healthy zero is a final answer. No path answers a failure with a different retrieval path, and no failure is relabeled as an empty success.

## How to read a row

The Test column names the test or tests that pin the row's disposition. A reference is `file :: test name`, or `file :: describe > test name` when the name is rendered from a table. A path without a directory is relative to the layer's source directory: `packages/memory-engine/src/` for engine and job rows, `packages/memory-bridge/src/` for bridge rows, `apps/api/src/` for HTTP rows and `apps/mcp/src/` for MCP rows. A reference that starts with a directory (`lib/capabilities.test.ts`) is relative to that source directory.

The Negative controls column pins the four outcomes a reader must be able to tell apart:

| Control | What it pins |
|---|---|
| Error | A failing query, driver call or dependency is a typed failure that reaches the caller. It is never an empty result. |
| Denial | A denied admission, ledger reservation or privilege is a typed denial. It is never a downgrade to a weaker path. |
| Absent | An absent index or capability is a typed failure naming what is missing. It is never a silent skip. |
| Zero | A healthy answer with no hits is a final, successful, empty answer. Nothing runs a second path to improve it, except a follow-up listed in the capability table of the deployment guide. |

`Also` lists a further test that pins a related clause. `Note` scopes a clause to another ticket. Text that starts with `n/a` says why the control cannot apply to that row. Text that names no test says which listed test carries the control.

Thirty-four rows had their read-scope, lifecycle or erasure clause owned by ticket T13, which was built in parallel with this matrix and is now merged. For those rows the Test column names the T13 tests that pin the clause. A Test cell that reads `no test: <why>` means T13 changed nothing at that layer, so no test of the layer pins the clause; the cell names the engine row that does, and the row's failure-path controls are still listed. Decision needed 9 lists those rows. A reference from another layer is written with its full path from the repository root.

## Decision needed

Each item is left as it stands on this branch. The lead rules on it.

1. **Standard-index retirement drops at boot (ruling 1, G4-79).** `ensureStandardIndexes` still has fifteen `dropIndex` call sites for retired standard (non-Search) indexes: fourteen by fixed name and the generic `dropCounterpartIfPresent` helper for TTL replacements. Most ignore a missing index. The sites are in `mongodb-schema-standard-indexes-core.ts`, `mongodb-schema-standard-indexes-graph.ts`, `mongodb-schema-standard-indexes-operations.ts` and `mongodb-schema-index-utils.ts` (`dropCounterpartIfPresent`). Decision 1a says startup creates or updates, never drops. Removing the drops leaves a redundant index live on an upgraded deployment and costs write amplification. Keeping them contradicts the rule. This branch changes neither, because the ruling decides which.
2. **Best-effort counters have no status surface.** `getBestEffortFailureCounts()` is in-process. Nothing reads it on `/v1/status`, `/v1/status/detailed` or `/v1/stats`, so an operator sees a counted failure only in the numeric-code log line. Affects every row that names a best-effort counter: E-46, E-47, E-48, J-08, J-09 and J-11. Surface it, or accept the log line.
3. **Planned zero-hit follow-ups (ruling 3).** The structured and procedure vector tiers run a native `$search` tier after a successful zero (`reason: "zero-hits"`), and three request-level backstops run on a successful zero only (`backstop:procedural-exact`, `backstop:procedural`, `backstop:hybrid`). All are ledger-accounted, visible in the outcome rows, and never triggered by a failure or a denial. They are documented as planned follow-ups under plan decision 5. Confirm that listing, or ask for each to be fused into one native query.
4. **Typed engine failures without an outcome row on non-search routes.** Review fix R8 audited every non-search route for a path to engine Search. Two reach it: `/v1/consolidate` (the consolidator's entity-batch `$search`, the similarity probe and the novelty scan) and `/v1/probes/vector` (the vector probe). A typed Search failure on them (a lane failure, `index-unavailable`, `index-stale` or a budget denial) now goes through the shared outcome and status mapper: 503 `SEARCH_LANES_UNAVAILABLE`, 503 `SEARCH_BUDGET_EXHAUSTED` with `Retry-After` where the denial carries a hint, or 500 `SEARCH_LANES_FAILED`, with the bounded `outcomes` row. An unrecognized error on either route stays the route-coded 500 with no engine text. `/v1/chain-trace`, `/v1/extract`, `/v1/profile`, `/v1/state`, `/v1/status`, `/v1/status/detailed`, `/v1/stats`, the lifecycle and admin routes and the write routes do not call a Search runner, so they never receive a typed Search failure; a typed engine failure there is still a route-coded 500 or a 503 (`SERVICE_UNAVAILABLE`) with no `outcomes` body, because those routes have no lane rows. `/v1/sync` answers a failed KB refresh as its own typed 500 (`KB_REFRESH_FAILED`, Decision needed 6). The E-46 and E-48 write receipts carry only `chunkCreated: false` when the projection fails; the failure itself is in the `projection_runs` row. Add an outcome body to the remaining routes, or accept the route code.
5. **J-08 episodes projection is not a durable retry job.** A failed projection is a `failed` run row plus a counter. It is not re-enqueued. Make it a queued job, or accept the failed row as the record.
6. **J-12 `maybeAutoRefreshKB`: file scan and read failures are still skipped.** A rejected import, an import that resolves with errors and a marker write that fails after a clean import are now a typed `KBRefreshError` (`KB_REFRESH_FAILED`, with `reason`, the import's commit counts and a bounded sample of its errors) that `sync` rethrows; the success marker never advances on any of them, so the next cycle re-attempts the whole refresh. An erasure conflict stays an explicit deferral (a warn line, no marker, no error). `ingestFilesToKB` still logs and skips a path it cannot scan or a file it cannot read without adding it to the result's `errors`, so a refresh over an unreadable file completes and writes the marker. Count those skips as import errors, or accept the log line. The refresh failure reaches `/v1/sync` as 500 `KB_REFRESH_FAILED` (`non-search-typed-failures.test.ts :: POST /v1/sync KB refresh failure (R7) > answers a failed refresh as 500 KB_REFRESH_FAILED naming the reason and the commit counts`), with a route-authored message that names the reason and what the import committed and carries no engine text and no `outcomes` body. A startup, watch or change-stream-gap sync that hits the same failure keeps its declared handling: a counted `startup-sync` best-effort failure, or a warn line.
7. **Catch blocks outside the matrix rows were not audited one by one.** Non-test engine source has 391 `catch` occurrences and 39 `.catch(` calls. The matrix rows above worked the inventory's swallowed-error entries that sit on a REBUILD or TYPED path. The other catch blocks (cleanup, probes, telemetry, audit and run-record writes) were not reviewed individually, and none is claimed to be typed or declared best-effort.
8. **Retry hints.** A per-request ledger denial carries no `retryAfterMs`, so it sends no `Retry-After`; only an admission denial with a finite positive hint does. The `/v1/search` admission denial stays a 200 with a `degradation` marker (plan decision R3); `/v1/search-kb` and `/v1/recall-conversation` answer it with a 503.
9. **Eighteen rows have no test for their T13 clause.** T13 added tests in the engine, the API and the MCP server where it changed a clause. These rows read `no test:` because T13 changed nothing at their layer: J-12; B-07, B-15, B-16, B-17, B-18, B-44, B-45, B-46; H-06, H-30, H-31; T-07, T-14, T-22, T-23, T-31 and T-32. Each forwards its input to the layer below, and the engine row it names pins the clause. Accept that pinning, or order a forwarding test per layer.
