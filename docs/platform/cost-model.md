# Cost model (per-tenant spend ledger)

Memongo records recurring provider spend in the `memory_cost_ledger`
collection and surfaces trailing 30-day sums at
`GET /v1/status/detailed?agentId=...` under `costLedger`:

```json
{
	"costLedger": {
		"windowDays": 30,
		"daily": [
			{
				"day": "2026-09-04",
				"inputTokens": 1200,
				"outputTokens": 300,
				"embedUnits": 9
			}
		]
	}
}
```

Days with no spend are absent from `daily` (a missing day spent nothing).
Ledger rows expire 90 days after their last update, which covers weekly and
monthly reporting cycles on the same data.

## What the counters mean

| Counter | Channel | Unit |
| --- | --- | --- |
| `inputTokens` / `outputTokens` | `llm` | tokens reported by the enrichment provider transport (`prompt_tokens`/`completion_tokens` for OpenAI-compatible gateways, `input_tokens`/`output_tokens` for Anthropic) |
| `embedUnits` | `indexing` | one write that triggers a server-side autoEmbed of an indexed field |
| `embedUnits` | `search` | one query-time lane probe (counted from the per-request search budget) |
| `embedUnits` | `cache-probe` | one query-cache tier-2 semantic lookup |
| `embedUnits` | `consolidation` | one consolidator similarity probe |

Embedding spend is counted in **operations**, not billable tokens: with
automated embedding the embed runs server-side inside mongot, and MongoDB
does not expose the token meter to the calling process. One unit = one
operation that embeds one indexed field. LLM token counts come straight from
the provider usage block, so they are exact; when a gateway does not report
usage, that call records nothing (call counts remain observable in the
telemetry channel).

## Converting counters to dollars

The ledger deliberately stores raw counters, not dollars: prices change on
the provider's schedule, not ours, and the operator knows which plan they are
on. Convert at read time with this table — replace the illustrative rates
with the numbers from your own price sheet, then regenerate the table when
either model changes.

| Counter | Rate source | Illustrative rate | Dollars per unit |
| --- | --- | --- | --- |
| `inputTokens` | price sheet for your `MEMONGO_ENRICHMENT_MODEL` | $3.00 / 1M input tokens | `inputTokens × 3.00 / 1_000_000` |
| `outputTokens` | price sheet for your `MEMONGO_ENRICHMENT_MODEL` | $15.00 / 1M output tokens | `outputTokens × 15.00 / 1_000_000` |
| `embedUnits` | price sheet for the autoEmbed model (`voyage-4-large`, the single source of truth in `packages/memory-engine/src/mongodb-schema-search-definitions.ts`) | $0.06 / 1M embeddings | `embedUnits × 0.06 / 1_000_000` |

Illustrative figures are round numbers chosen to show the arithmetic, not
quoted prices; look up the current rates before billing anything. The
workday computation, for a tenant with `inputTokens: 1_200_000`,
`outputTokens: 300_000`, `embedUnits: 9_000` on one day:

```
llm   = 1_200_000 × 3.00 / 1M  +  300_000 × 15.00 / 1M  = $3.60 + $4.50 = $8.10
embed = 9_000 × 0.06 / 1M                                     ≈ $0.0005
total ≈ $8.10
```

## Regenerating the table

The table above is regenerated by hand whenever a model or price changes:

1. Look up the current per-token rates for the enrichment model configured in
   `MEMONGO_ENRICHMENT_MODEL` (and `MEMONGO_ENRICHMENT_PROVIDER`, which
   decides which usage fields the transport reads).
2. Look up the current per-embedding rate for the autoEmbed model pinned in
   `INDEX_AUTOEMBED_MODEL`.
3. Update the "Illustrative rate" column and recompute the worked example.

The counters themselves never change shape: any future pricing only changes
the multiplier column, which is why the ledger stores raw counts.
